# 字幕节奏与镜头边界校正台（Subtitle Rhythm & Shot-Boundary Correction Station）

本地运行的 Web 应用：导入 **SRT / WebVTT** 字幕与含镜头起止毫秒的 **JSON**，
按 **Unicode 扩展字素簇（UAX #29）** 计数，检查重叠、空隙、每秒字符数（CPS）
与跨镜头切换；在「只平移、不改时长」的前提下搜索确定性最优校正方案，
支持逐条采纳并导出带**原文哈希、校正版本、冲突说明**的 JSON。
含镜头的项目还可以在项目页进行**镜头留白审阅**：按生效时间轴找出每个
镜头内未被字幕覆盖的区间，逐条标记「有意留白 / 待补字幕」。

项目页支持**逐条文案修订与恢复导入原文**：导入时即保存每条的原始文本、
可见文本、字素数与原文哈希；修订保存时沿用同一套去标签、折叠空白与
Unicode 字素簇规则得到非空当前文案。生效文案（修订稿 ?? 导入原文）即时
参与 CPS 告警、生效轴指纹与 JSON / SRT / ZIP 导出；原文哈希始终指向导入
内容，cue_id、原时间、采纳与镜头留白结论不受修订影响。另一标签页先改过
同一条时，保存会被拒绝并自动刷新显示最新文案，不会覆盖他人修改。

项目页还提供**交付字幕核验**：上传合作方回传的 SRT / WebVTT，服务端复用
字幕解析，将可见文本与起止毫秒与项目当前生效时间轴（已采纳 → 提案 → 原值）
保序对照，逐条给出**通过 / 时间不符 / 缺失 / 新增 / 待确认**结论与数量。
核验结论与生效时间轴**绑定**（指纹含生效文案），且以**提交动作**为稿件
切换边界：页面只记住最近一次点「上传并核验」提交的稿件——只在文件框改选
另一份而不提交、或清空文件框，都不会切换稿件；改参数、采纳、撤销或修订
文案改变了生效轴后，页面自动用**最近一次已提交且仍可读取**的稿件按新轴
重新核验（不会把改选未提交稿件的结论当作旧稿的，改选稿只有提交后才取代
旧稿；稿件不可读时作废旧结论、提示重传），不会继续显示旧结论；另一标签页
改轴导致本页详情过期时，页面先拉取最新项目详情再裁决——结论按新详情仍
有效则直接接纳展示，已过期才用已提交稿件按新轴重核，自动重核有终止条件，
不会循环发请求。核验为只读操作，不更改采纳、留白结论与 JSON / SRT / ZIP
导出。

## 技术栈

- 后端：Python 3.11 + FastAPI + SQLite（`fastapi` / `uvicorn` / `regex`）
- 前端：原生 HTML + CSS + JavaScript（无构建、无框架）
- 部署：Docker Compose 一键启动，数据持久化在命名卷中

## 一键启动（Docker Compose）

```bash
docker compose up -d --build
```

启动后浏览器访问：

> **http://localhost:8000/**

（间隔/CPS/跨镜头/冲突数量）、逐条提案与 Δ、冲突链说明，并可逐条采纳、
逐条修订文案、导出 JSON / SRT / ZIP 校正结果。接口文档见
http://localhost:8000/docs 。

**访问已修订的项目**：修订稿与项目一起持久化在命名卷 `subtitle-data`
中——`docker compose up -d --build` 启动后打开 http://localhost:8000/ ，
在页面右上角「选择历史项目」下拉框选中之前导入的项目，工作区表格的
「文案」列即显示当前生效文案（已修订的条目标注「已修订」徽标并附导入
原文），可继续修订、恢复原文或导出。重启容器、重建镜像（不带 `-v` 的
`down`）都不会丢失修订；`docker compose down -v` 才会连同项目一起删除。

项目页底部「交付字幕核验」区上传回传稿即可核验；此后在页面上修改参数
（应用参数重新求解）或采纳 / 撤销条目时，无需手动重传——生效时间轴一旦
变化，核验区会自动用**最近一次已提交**的稿件按新轴重新核验并刷新结论
（只在文件框改选了另一份而不提交不会换稿，清空文件框但已提交稿件仍可读取
时也继续用该稿；稿件已不可读时旧结论作废并提示重新上传）；仅调 CPS 上限等
不改变生效轴的修改会保留原结论。

**镜头留白审阅入口**：导入（或在右上角选择）含镜头 JSON 的项目后，
项目页（工作区）表格下方的「镜头留白审阅」区即列出每个镜头的留白区间，
可直接标记结论；无镜头的项目不生成审阅项、该区域不显示。详见
[下方「镜头留白审阅」](#镜头留白审阅)。

**交付字幕核验入口**：打开任意项目后，项目页底部「交付字幕核验」区上传
回传稿（`.srt` / `.vtt`）即可看到逐条结论与通过 / 时间不符 / 缺失 / 新增 /
待确认数量；无需镜头数据，所有项目均可核验。此后修改参数、采纳或撤销：
若生效时间轴发生变化，页面会**自动用最近一次已提交的稿件按新轴重新核验**
（只在文件框改选未提交不会换稿、清空文件框也不影响；稿件不可读时旧结论
作废、提示重新上传）；若生效轴未变（如仅调 CPS 上限），原结论保留。
详见[下方「交付字幕核验」](#交付字幕核验)。

**改选未提交后的结论**：先提交甲稿得到结论，随后只在文件框改选乙稿而
**不点「上传并核验」**，此时稿件并没有切换——本页改参数改变生效轴，或
跨标签页变轴后本页刷新详情仍需重核时，自动重核携带的始终是甲稿，页面
不会把乙稿的结论当作甲稿的；乙稿只有在**提交之后**才取代甲稿。清空文件框
但甲稿仍可读取时，自动重核继续用甲稿。访问方式同上：
`docker compose up -d --build` 后打开 http://localhost:8000/ ，在项目页底部
操作即可。

**跨标签页改轴后查看结论**：可以用两个浏览器标签页同时打开
http://localhost:8000/ 并选择同一项目——在一个标签页修改最小间隔等参数
（或采纳 / 撤销），另一个标签页的核验区无需手动刷新：它在下一次核验
（手动提交或自动重核）时发现响应指纹与本页详情不符，会先自动拉取该项目
最新详情——结论按新详情仍有效则直接展示（页面详情同步到最新），已过期
才用最近一次已提交的稿件按新轴重核。自动重核有终止条件（一条重核链最多
连续 3 次核验请求）；详情刷新失败、已提交稿件不可读或达到上限时停止并
提示重新上传。页面不会停留在旧结论，也不会反复发请求。

页面上若在一个标签页改参数的同时另一个标签页（或脚本）正在采纳，两个
写操作会在服务端自动排队：后提交的一方看到的始终是**另一方提交后的
最新状态**——先到的采纳若在新参数下失效会被自动撤销，先到的新参数会让
迟到的旧提案被拒绝；刷新后表格、统计条与导出的校正结果即与终态一致。
详见[下方「并发：参数更新与采纳交错」](#并发参数更新与采纳交错)。

## 使用流程

1. **导入素材**
   - 字幕：`.srt` 或 `.vtt`（自动识别；计数时去除标签、折叠空白，
     按扩展字素簇计数，空格计入字符，CJK 与 emoji 组合序列按 1 个可见字符计）。
   - 镜头 JSON（可选）：
     ```json
     [
       {"start_ms": 0,    "end_ms": 1200},
       {"start_ms": 1200, "end_ms": 3050}
     ]
     ```
     也接受 `{"shots": [...]}` 外层，字段名兼容 `start/end`、`in/out`、
     `start_ms/end_ms` 等毫秒字段。
2. **设置参数**
   - **CPS 上限**：每秒字符数告警阈值（平移不改变时长，CPS 仅作检测告警，
     无法通过平移修复时会在条目上标注）。
   - **最小间隔（ms）**：相邻条目之间允许的最小空隙；重叠（负值）与过小空隙
     都会被检出。
   - **镜头边界容差（ms）**：每个镜头**独立**参与判断（相接或重叠的镜头
     不做合并），条目整体必须落在某一个镜头内；起点可在 `原起点 ± 容差`
     内平移，且平移后条目不跨过镜头切点。原字幕一旦跨越切点即标记
     「跨镜头」，与容差无关；恰好始于或止于切点视为合法。
3. **查看结果**
   - 统计条：间隔/重叠、CPS、跨镜头、可提案、需移动、冲突数量与总移动量。
   - 表格逐行显示生效文案（已修订的附导入原文）、原文哈希、原时间、
     字素数、CPS、问题标记、提案时间与 Δ。
   - 无法满足约束的 cue 以**冲突链**形式列出（含导致失败的相邻关系说明）。
4. **逐条采纳**：每行「采纳 / 撤销」，或顶部「采纳全部提案」；采纳状态持久化。
5. **逐条文案修订**（可选）：每行「修订」进入行内编辑，保存时去标签、
   折叠空白、按字素簇计数（空白稿被拒绝）；「恢复原文」回到导入文案。
   修订即时反映到 CPS 告警、导出与交付核验的生效轴指纹；原文哈希不变。
6. **镜头留白审阅**（含镜头的项目）：工作区表格下方列出每个镜头内未被
   字幕覆盖的区间，逐条标记「有意留白 / 待补字幕」，可随时「清除」回到待审。
7. **交付字幕核验**：工作区底部上传合作方回传的 SRT / WebVTT，页面给出
   逐条结论（通过 / 时间不符 / 缺失 / 新增 / 待确认）与数量。结论与当前
   生效时间轴绑定，并以**提交动作**为稿件切换边界：参数重算、采纳、撤销
   或文案修订改变生效轴后自动用**最近一次已提交且仍可读取**的稿件重新
   核验（只在文件框改选未提交不换稿、清空文件框不影响；稿件不可读时作废
   并提示重传）；另一标签页改轴导致本页过期时，先同步最新详情再决定接纳
   或重核（自动重核有次数上限）；切换项目后仅显示当前项目最近一次提交
   的结果。
8. **导出**
   - `JSON`：含项目参数、每条原文 SHA-256（始终指向导入内容）、生效文案
     与导入原文 / 修订标记、`original` / `proposal` / `corrected` 三套
     时间、状态以及完整冲突说明，并带整包 `document_hash`。
   - `SRT`：导出采纳后的时间轴（未采纳者回退提案、再回退原值），文案为
     当前生效文案。
   - `ZIP`：同时包含上述 JSON 与 SRT。

## 字幕时间轴的核对方法

页面与接口看到的时间轴始终遵循同一条**有效时间轴**规则：
**已采纳 → 提案 → 原值**（仅平移，时长永不改变）。可按下面方式核对：

1. **页面表格**：「当前时间」列对已采纳行显示采纳值，未采纳行显示原值；
   「提案」列显示新参数下的提案，「Δ」列是提案相对原起点的平移毫秒数；
   行首状态徽标为「已采纳 / 待采纳 / 冲突」。
2. **逐条核验**：对任意一条 cue，其导出时间应为
   - 已采纳：`adopted_start_ms / adopted_end_ms`（`corrected` 字段相同）；
   - 未采纳且有提案：`proposal_start_ms / proposal_end_ms`；
   - 冲突无提案：原始 `start_ms / end_ms`。
   时长 `end − start` 必须始终等于原时长。
3. **改参数后复核**：修改 CPS / 最小间隔 / 容差并提交后，表格与统计条会
   整体重算；不再合法的采纳自动变回「待采纳 / 冲突」。可用下方接口自行
   比对（以 `jq` 为例）：
   ```bash
   curl -s localhost:8000/api/projects/1 | jq '.analysis.cues[]
     | {cue_id, original:[.start_ms,.end_ms],
        proposal:[.proposal_start_ms,.proposal_end_ms],
        adopted:[.adopted_start_ms,.adopted_end_ms]}'
   ```
4. **两种 SRT 必须一致**：独立 SRT（`?fmt=srt`）与 ZIP 内的 `corrected.srt`
   使用同一条有效时间轴，字节级时间戳应完全相同；JSON 导出
   （`?fmt=json`）里每条的 `original / proposal / corrected` 三套时间
   分别保留原值、提案与**仅存的合法采纳**，`corrected` 为 `null` 即该条
   当前无有效采纳。
5. **典型用例**：导入 0–1000ms 与 1000–2000ms 两条字幕（最小间隔 40ms、
   容差 200ms），提案为 0–1000ms、1040–2040ms。只采纳第一条后再次用相同
   参数提交：第一条仍为「已采纳」；两种 SRT 中第一条是 0–1000ms，
   第二条是提案 1040–2040ms（而不是原值 1000–2000ms）。

## 参数变更与采纳状态重核验

更新 CPS 上限 / 最小间隔 / 边界容差时，系统会在**同一事务**内用新参数
重新核验每一条已采纳记录，核验规则与求解器约束一致：

- **仅平移**：新时长必须与原时长完全一致；
- **容差**：`|新起点 − 原起点| ≤ tolerance_ms`；
- **镜头边界**：平移后整体落在某一个镜头之内；
- **最小间隔**：与相邻条目的**生效位置**保持 `min_gap_ms`；生效位置与
  SRT 导出共用同一条有效时间轴——**已采纳取采纳值，未采纳先取新参数
  下的提案，无提案再取原值**（撤销一条后其邻居改按提案/原值重新参与
  核验，按轮次到达不动点）。

仍满足全部约束的采纳**保持有效**；不再满足的采纳被**撤销**，条目回到
「待采纳 / 冲突」状态。项目详情、项目列表、采纳按钮与 JSON / SRT / ZIP
三种导出统一使用重核验后的状态——失效的采纳时间不会出现在导出的
`corrected` 中。若重算过程失败，参数与采纳状态**整体回滚**，
不会留下半更新。

例如：镜头 `[0,1200)`、`[1200,2400)` 与 900–1300ms 字幕，容差 200ms 下
采纳提案 800–1200ms；把容差改为 50ms 后，该采纳因超出容差被撤销，
详情显示冲突链，三种导出的 `corrected` 均为空、时间轴回退原值。

又如：两条相接字幕 0–1000ms、1000–2000ms，最小间隔 40ms、容差 200ms，
提案为 0–1000ms、1040–2040ms。只采纳第一条（0–1000ms）后即使以**完全
相同的参数**再次提交，第一条也不会被误撤销：相邻的第二条未采纳，按其
提案 1040ms 参与间隔核验，1000→1040 恰为 40ms。

## 逐条文案修订与恢复导入原文

项目页表格「文案」列对每条字幕提供**修订**与**恢复原文**：

- **导入原文与修订稿的区分**：导入时即落库每条的原始文本（`raw_text`）、
  可见文本（`text`）、字素数（`graphemes`）与原文哈希（`raw_hash`），
  这四项导入后永不改变。修订稿单独存放（`edited_text` /
  `edited_graphemes`，`NULL` 表示未修订）——**生效文案 = 修订稿 ??
  导入可见文本**，生效字素数同理。页面已修订的条目标注「已修订」徽标
  并附导入原文对照；JSON 导出同时给出 `text`（生效文案）、
  `imported_text`（导入可见文本）与 `edited` 标记。
- **保存归一化**：修订保存时沿用导入同一套规则——去标签、折叠空白、
  按 Unicode 扩展字素簇计数——得到**非空**当前文案；归一化后为空的
  空白稿（纯空白、去标签后无内容）返回 `400` 且不写入任何内容。
- **生效文案即时生效**：详情用生效文案与生效字素数计算 CPS（修订可
  消除或引入 CPS 告警，统计条同步变化）；生效轴指纹 `timeline_hash`
  含生效文案，修订或恢复后指纹必变，交付核验的旧结论按现有指纹机制
  作废旧结论、用已提交稿件自动重核；JSON / SRT / ZIP 的文案同步更新。
  **不变的**：`raw_text_hash` 仍指向导入内容，`cue_id`、原时间、采纳
  与镜头留白结论保持原样（留白区间只由时间轴决定，与文案无关）。
- **旧页面识别与并发**：修订 / 恢复请求携带 `base_text`（进入编辑时
  看到的生效文案）。服务端在写锁内比对当前生效文案——另一标签页先改
  过同一条（生效文案已不等于 `base_text`）时返回 `409` **拒绝覆盖**，
  前端随即退出编辑并拉取最新详情，页面显示最新文案；两个写操作在
  服务端写锁上串行，后到者看到的必为先到者提交后的最新状态。编辑
  期间若详情被外部刷新（生效文案已变），页面自动退出编辑态。
- **原子性**：空白稿、不存在的 cue（`400`）、不存在的项目（`404`）、
  `base_text` 过期（`409`）或保存中途失败，都不会留下部分写入——
  校验与落库在同一写事务内，任一步失败整体回滚。

接口：

- `PUT /api/projects/{pid}/cues/{cue_uid}/text`：修订文案，Body 为
  `{text, base_text}`；成功返回最新项目详情。
- `POST /api/projects/{pid}/cues/{cue_uid}/text/reset`：恢复导入原文，
  Body 为 `{base_text}`；未修订时为幂等空操作。

修订稿随项目持久化（SQLite 命名卷），删除项目时级联清除；旧版本库
首次启动会自动迁移（`cues` 表补 `edited_text` / `edited_graphemes`
列），已存数据不受影响。

## 镜头留白审阅

含镜头 JSON 的项目，项目页（工作区）表格下方出现「镜头留白审阅」区；
**无镜头时不生成任何审阅项**。服务端按与 SRT 导出相同的**生效时间轴**
（已采纳 → 提案 → 原值）计算每个镜头内未被字幕覆盖的**半开毫秒区间**
`[start, end)`：

- 字幕覆盖先**裁剪到各镜头**内，**重叠或相接**（端点相贴）的覆盖段
  合并后再取补集；
- **相接或重叠的镜头分别审阅**，各自独立计算，不做镜头合并；
- 完全没有任何字幕覆盖的镜头以**整段** `[shot_start, shot_end)` 为一条
  审阅项。

每条留白列出起止时间（`hh:mm:ss,ms` 与原始毫秒）和时长，审阅者可标记
**有意留白** 或 **待补字幕**（可随时「清除」回到待审），结论持久化在
`gap_reviews` 表中，随项目删除级联清除。接口：

- `GET /api/projects/{pid}`：响应的 `gap_review.items` 列出全部留白项
  及其当前结论（`null` 即待审）；
- `POST /api/projects/{pid}/gaps/review`：提交结论，Body 为
  `{shot_ord, gap_start_ms, gap_end_ms, decision}`，`decision` 取
  `intentional` / `needs_subtitle`；
- `DELETE /api/projects/{pid}/gaps/review?shot_ord=&gap_start_ms=&gap_end_ms=`：
  清除结论，回到待审。

### 审阅项身份与状态迁移

审阅项身份 = **镜头（ord + 镜头边界）+ 留白起止毫秒**。采纳、撤销或
参数重算改变生效时间轴、进而改变留白边界时：

- 同一镜头中**边界未变**的留白，结论**保留**；
- 边界发生变化的区间匹配不到旧结论，回到**待审**；参数重算 / 采纳 /
  撤销三条写路径会在**同一事务**内清除不再匹配任何当前留白的过期结论；
- **过期页面**（另一标签页已改参数或采纳）提交的结论，在写锁内按最新
  状态重算校验：区间已不存在则 **400 拒绝**，前端收到后自动刷新，
  不会把结论误标到变化后的新留白上。

审阅结论不参与校正与导出：JSON / SRT / ZIP 导出语义与之前完全一致。

## 交付字幕核验

项目工作区底部的「交付字幕核验」区上传合作方**回传稿**（`.srt` / `.vtt`，
与导入共用同一套 SRT / WebVTT 解析）后，服务端把每条可见文本（去标签、
空白折叠后的同一套归一化）和起止毫秒，与项目**当前生效时间轴**对照——
生效时间轴与 SRT 导出完全一致：**已采纳 → 提案 → 原值**。

交付稿经常被合作方**重编号、插删行、重复文案、拆并行**，因此：

- **不按 cue_id 或行号配对**，而是在「生效轴条目 → 交付稿条目」两条保序
  序列之间求一一对应（不交叉；拆并行保持独立、**不自动合并**）；
- 对应规则按字典序严格择优：
  1. **同文案匹配对数最多**；
  2. 并列时，匹配对的**起止时间偏差绝对值之和最小**
     （`Σ|Δ起| + |Δ止|` 毫秒）。
- 逐条结论：
  - **通过**：匹配且起止毫秒**完全相同**（两者有任一不同都不算通过）；
  - **时间不符**：已匹配但起止毫秒存在差异，页面同时显示 `Δ 起 / Δ 止`；
  - **缺失**：生效轴有、交付稿中没有；
  - **新增**：交付稿有、生效轴中没有；
  - **待确认**：存在多个**等优对应**（同文案对数与偏差和都相同）且会改变
    某行结论时，把涉及行列为待确认，**不强判**缺失 / 时间不符 / 新增；
    页面会附上等优候选（偏差最小的另一侧条目）供人工确认。

统计条给出五类结论各自的数量。空稿、只含注释块或解析失败返回 `400`
并提示原因，不出结果。核验是**只读**操作：结果不落库，重新上传即重新计算；
不更改任何采纳、留白审阅结论，JSON / SRT / ZIP 导出与核验前**字节级一致**。

### 核验结论与生效时间轴绑定

核验结论只对「**该项目、该生效时间轴、该次提交**」有效。稿件切换以
**提交动作**（点「上传并核验」）为唯一边界：前端只保存最近一次提交时的
稿件快照（File 对象与文件名，页面内存态、不落库），项目详情与
`verify-delivery` 响应携带同一个 `timeline_hash`（生效轴指纹：逐条
ord / cue_id / 生效文案 / 生效起止毫秒的 SHA-256），页面据此绑定：

- **提交才换稿，改选未提交不换稿**：提交甲稿后只在文件框改选乙稿而不
  提交，`files[0]` 虽已是乙稿，但自动重核的两条路径（本页变轴、跨标签页
  变轴后刷新详情仍需重核）一律读取**最近一次已提交的甲稿快照**，不会把
  乙稿的结论当作甲稿的；乙稿只有在提交之后才取代甲稿。**清空文件框**
  同样不影响快照：只要甲稿 File 仍可被页面读取，自动重核继续用甲稿。
- **稿件不可读则作废提示重传**：已提交稿件的 File 句柄已不可读（如浏览器
  回收）时，自动重核请求无法携带该稿而失败，旧结论立即作废并提示重新
  上传，不会回退使用文件框里改选未提交的稿件。
- **生效轴变化即作废**：参数重算、采纳、撤销、文案修订或恢复改变了生效
  时间轴（指纹变化，指纹含生效文案）后，旧结论**立即从页面移除**——
  已提交稿件快照仍可读取时，自动用该稿按新生效轴**重新核验**并展示新
  结论；不可读时提示重新上传。
  例如：相接两条字幕 0–1000ms、1000–2000ms，最小间隔 40ms 时回传稿按
  提案 1040ms 核验全部通过；把最小间隔改为 100ms 后提案变为 1100ms，
  页面不会停留在旧的「通过」，而是自动用已提交的那份回传稿重核并显示
  第二条**时间不符**（Δ 起/止 −60ms）——即便此时文件框里改选的是另一份
  未提交稿件。
- **生效轴未变则保留**：仅调 CPS 上限、相同参数重复提交、采纳值即提案值
  （未采纳本就回退提案）等不改变生效轴的操作，以及参数校验失败（`400`）
  时，已展示的有效结论**保留**，不重复请求。
- **指纹不符先同步详情再裁决**（跨标签页改轴）：核验响应的指纹与本页
  详情不符时，本页详情可能已过期（另一标签页改了参数 / 采纳）。页面先
  拉取该项目**最新详情**：响应指纹与最新详情一致，说明已返回的结论按
  新详情仍然有效，直接接纳并把页面详情同步到最新；仍不一致（等待期间
  生效轴再次变化）才用最近一次已提交且仍可读取的稿件快照按新轴重核。
  自动重核有**终止条件**：一条重核链最多连续 3 次核验请求；详情刷新失败、
  快照不可用或达到上限时立即停止——作废旧结论并提示重新上传，不显示
  旧结论、不无界发请求。
- **并发只呈现最近一次**：每次提交与递增序号绑定；提交或详情刷新未完成
  时切换项目、再次提交或删除项目，迟到的响应一律丢弃——页面只呈现
  **当前项目最近一次有效提交**的结果；响应到达时若生效轴已再次被改变
  （另一标签页改参数 / 采纳），按上一条的「先同步详情再裁决」处理。

接口：

- `POST /api/projects/{pid}/verify-delivery`（`multipart/form-data`，
  字段 `delivery` 为回传稿）→
  ```json
  {
    "project_id": 1, "project_name": "示例", "delivery_name": "back.srt",
    "timeline_hash": "d8b99d98…",
    "reference_count": 2, "delivered_count": 3, "matched_text_count": 1,
    "summary": {"pass": 1, "time_mismatch": 0, "missing": 1,
                "new": 1, "pending": 0},
    "rows": [
      {"kind": "match", "verdict": "pass", "ref_ord": 1, "cue_id": "1",
       "text": "甲", "ref_start_ms": 0, "ref_end_ms": 1000,
       "del_ord": 1, "delivered_text": "甲",
       "del_start_ms": 0, "del_end_ms": 1000,
       "delta_start_ms": 0, "delta_end_ms": 0, "text_same": true}
    ]
  }
  ```
  `project_id` 与 `timeline_hash` 和项目详情接口同源：调用方应只在
  「仍是当前项目且指纹一致」时展示结论；指纹不符时先请求项目详情刷新
  本地指纹——与最新详情一致即可接纳，仍不符再按最新生效轴、用同一份
  已提交稿件重核。前端以提交动作保存稿件快照，自动重核不读取文件框
  当前值。
  `rows` 按保序对应排列：`kind`
  为 `match`（配对待确认/通过/时间不符）、`ref_only`（缺失或待确认）、
  `del_only`（新增或待确认）；待确认行带 `candidate`（另一侧的等优候选
  条目）。

对应算法为前向 + 后向两张序列对齐 DP（O(生效条目 × 交付条目)），
真实交付稿（数百至千条）在秒级完成；两侧条目超过 3000 时返回 `400`，
提示拆分稿件。回归见 `tests/test_delivery_verify.py`（单元等优歧义 +
端到端生效时间轴 / timeline_hash 绑定 / 空稿 / 导出不变）与
`tests/test_delivery_verify_frontend.js`（前端绑定：提交动作才切换稿件 /
改选未提交与清空文件框不影响已提交快照 / 过期作废 / 自动重核 /
跨标签页改轴时先同步详情再裁决 / 重核终止条件 / 并发与切换项目丢弃
迟到响应）。

## 并发：参数更新与采纳交错

页面提交 `PUT /api/projects/{pid}/settings`（收紧容差或最小间隔）与
`POST /api/projects/{pid}/adopt`（按提案采纳）可能同时到达。两条写路径
都遵循**同一事务边界**：进入处理时先以 `BEGIN IMMEDIATE` 取得该库的
写锁，**然后**才读取项目参数、字幕、镜头与已采纳状态；参数读取、
`build_analysis` 提案求解、采纳核验与落库全部在这一个写事务内完成。
后到的请求在写锁上等待（忙等上限默认 30s，可用环境变量
`BUSY_TIMEOUT_MS` 调整），持锁方提交后在锁内**重读最新状态**再继续，
因此两种交错顺序都不会让新参数与失效采纳并存：

- **采纳先提交**：设置事务等到写锁后，读到的就是含该采纳的最新状态；
  用新参数求提案并经 `revalidate_adoptions` 重核验时，新参数下失效的
  采纳在同一事务内被撤销，仍合法的采纳保留。
- **设置先提交**：采纳事务等到写锁后，按新参数重新求解并校验；若请求
  携带的是旧参数下的提案位置、而新参数下已无此提案或位置改变，采纳被
  拒绝（`400`），不写入任何采纳记录。

任一步失败（求解异常、约束不合法等）都会整体回滚，参数与采纳状态
**不留半更新**。详情接口与 JSON / SRT / ZIP 导出同样在只读事务的
一致快照内读取与求解，呈现的永远是重核验后的状态，失效采纳不会进入
导出的 `corrected` 与 SRT 时间轴。并发回归见
`tests/test_concurrent_settings_adopt.py`（门控两种提交顺序）。

## 求解器说明（确定性最优）

对每一个与冲突链不相交的**连续可解后缀段**独立求解，搜索空间为各条目在
「单镜头窗口 ∩ 原起点 ± 容差」内的所有整数毫秒起点（每个镜头各自生成
窗口，相接镜头不合并，因此切点永远不可跨越），约束为：

- `t[i-1] + duration[i-1] + min_gap ≤ t[i]`
- 条目整体位于某一镜头窗口内（恰在切点开始/结束允许）
- 仅平移，`duration` 保持原值

项目详情、参数重算、页面标记与采纳校验均经由同一套 `build_analysis`
规则实时重算，任何入口看到的跨镜头标记、提案与冲突链完全一致。

采用整数区间上的**分段线性动态规划（后缀极小包络）**精确求解，择优按
字典序严格排列：

1. **总移动毫秒** `Σ|t_i − original_i|` 最小；
2. 并列时，**发生移动的条目数**最少；
3. 再并列时，按 **`cue_id` 字典序**排列的绝对偏移向量字典序最小
   （越靠前的 cue_id 越优先保持原位；正负向偏移相同时取较小起点）。

权值采用超递增整数系数（Python 大整数精确运算，无浮点比较），
因此相同输入永远产生唯一、确定的输出。不存在可行解的条目归入**冲突链**：
链是连续的不可解段，说明中给出硬阻断的相邻 cue 对或“无镜头窗口可容纳”等
内在冲突原因。
